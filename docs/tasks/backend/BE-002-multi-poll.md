## PM decisions
| Topic | Decision |
|---|---|
| Max polls per connection | 16 (the 17th is `validation`, field `polls`) |
| Poll names | unique per connection, case-insensitive, 1-48 chars, DES-002 section 4 |
| Poll ids | `u32`, unique per session, never reused, runtime only (not saved) |
| Scheduling | exactly DES-002 section 7: one request in flight, writes FIFO first, earliest `nextDue`, ties to least recently served, no catch-up, no starvation; **list order and host never affect scheduling** |
| Connection vs poll state | `ConnectionState` (idle, connecting, connected, disconnected; C1-C7) and `PollState` (offline, paused, polling, timeout, exception, badResponse; PT0-PT8) exactly as DES-002 section 1; only socket/port errors cause `disconnected`; a poll's timeout/exception/badResponse never changes the connection state |
| Routing | one event stream (Tauri `Channel`) per attached poll view (workspace sub-window in W1 or native W2), at most one attached view per poll, view tokens; attach/detach/pop out/dock/close only change routing and stored UI fields, never the scheduler, link or counters (DES-002 8.1) |
| Scale | frontend only. Rust stores/relays `ScaleSettings`, `ScaleOverride`, `ValueColumns`, `aliases` as typed view settings and writes them to profiles; Rust never interprets scale. Validate only shape and size limits (<= 64 overrides per poll, strings <= 16 chars, aliases per DES-002 section 4: <= 2000, unique address, text rules) |
| Profiles | schema 2 as DES-002 6.1 (changed in place, nothing shipped); `profiles_get` migrates schema 1 -> 2 (`migratedFrom: 1`, the file stays v1 until saved); schema >= 3 stays unreadable; schema 2 with > 16 polls, invalid poll, invalid alias list or invalid `minimizedOrder` is `invalidProfile` (`readable: false` in the list); `profiles_save` writes v2 and validates; keep the permissive-draft rule and cheap checks of BE-001 |
| Layout values | stored and relayed only (no geometry decisions in Rust except `mm_arrange_poll_windows` and native window placement); UI-only values never mark the profile modified (that is a frontend rule, but expose a separate `layoutRevision`/no flag so the frontend can tell: export includes them, apply restores them) |
| Windows | thin Tauri layer. Native poll window label `modbus-master-<n>-poll-<pollId>`, route `/tools/modbus-master/poll`, minimum size 480 x 320, created unowned; capabilities `windows` pattern must match these labels and grant only the window permissions the frontend really uses (read `apps/desktop/src/shared/ipc` read-only to check; the frontend may add calls: re-check at the end) |
| Arrange | `mm_arrange_poll_windows` implements DES-002 2.8 for NATIVE windows only. Put the layout math in a pure, testable function (crate `platform` or a module in `src-tauri` without Tauri types) and test it with the DES-002 2.8 test vectors; the Tauri call just applies rectangles |

## Final contract (backend, 2026-10-16; phase 1)

This section is authoritative for the frontend and QA. Types are generated into `apps/desktop/src/shared/bindings/` (`pnpm bindings`, 76 files); import them from `@/shared/bindings`. All JSON is camelCase. Timestamps (`at`, `lastOkAt`, `modifiedAt`) are ms since the Unix epoch. `invoke` rejects with `AppError { code, message, field }`. BE-002-1 (types) was published first; no type was renamed after that.

### Windows and sessions
- One session per connection window W1 (label `modbus-master-<n>`), created by `mm_open_session`. Native poll windows W2 have the label `modbus-master-<n>-poll-<pollId>` and the route `/tools/modbus-master/poll?pollId=<pollId>` (the poll id is in the query and in the label). W2: default 900 x 640 client, unowned (own taskbar entry), created hidden, placed, then shown and focused. **Minimum: 480 x 320 OUTER** (PM decision on REV-004 M1; title bar and borders included, the same rectangle arrange and pop out compute). The window is built with the client minimum (480 x 320) minus a conservative fallback frame of 32 x 64 logical px (= 448 x 256); right after creation its frame (outer size minus client size, converted to logical px with its scale factor, rounded up) is measured and the client minimum becomes (480 x 320) minus that frame (Windows 11 at 100 %: 16 x 39, so 464 x 281). A W2 at its minimum is therefore exactly 480 x 320 outside, and the NT-2 / NT-3 cells (640 x 344, 480 x 344) fit three rows into a 1032 px work area.
- Every command can be invoked from W1 or from one of its W2 (it resolves to W1's session), except: `mm_open_session` (W1 only; from a W2 `invalidState`) and `mm_attach_poll_view` (W1 attaches `host: "workspace"` views; a W2 attaches only its own poll with `host: "native"`, else `validation` with `field: "host"` or `"pollId"`).
- Teardown: when W1 is destroyed its session stops (link closed, tasks ended) and every W2 of that connection is destroyed. When a W2 is destroyed without `mm_close_poll_view` / `mm_dock_poll`, its route is dropped and the poll becomes closed (kept); `PollListChanged` follows. A view channel whose webview is gone is dropped on the next failed send (no sender leak).
- Capabilities: unchanged permissions (`core:default`, `core:window:allow-set-title`, `core:window:allow-destroy` for `main` and `modbus-master-*`, which also matches the W2 labels); only the description was updated. Re-checked against `apps/desktop/src/shared/ipc` at the end: the frontend uses `setTitle`, `onCloseRequested` and `destroy`; `app_list_monitors` is a command.

### Events
**W1 `Channel<SessionEvent>`** (discriminant `type`, payload fields flattened):
- `ConnectionStateChanged` (`ConnectionStatus`: `state, reason, config, at`): never dropped or coalesced. Poll failures never change it.
- `PollStateChanged` (`PollStatus`: `pollId, state, consecutiveFailures, exceptionCode, badResponseKind, badResponseDetail, at`): every poll, transitions PT1-PT7, never dropped or coalesced. A repeated ok cycle is not re-emitted; repeated failures are emitted with the incremented count. PT0 is reported only through `PollListChanged` (Q-BE2-04).
- `PollListChanged` (`{ polls: PollSummary[] }` in list order): after add, duplicate, remove, rename, apply, `active`, view settings, `hasUnappliedEdits`, host, `open`, workspace rectangle, reorder, profile apply.
- `TrafficFrames` (`{ frames }`): at most one batch per 50 ms; 5,000 frames kept per connection.
- `Counters` (`ConnectionCounters`: `total, writes, polls: PollCounters[]` in list order, `linkLoadPct`): at most one per 100 ms, latest wins.
- `RevealPoll` (`{ pollId, workspaceRect: WorkspaceRect | null }`), `PrefsChanged` (`{ askOnPollClose, compact }`), `SaveRequested` (`{ saveAs }`), `ShowTraffic` (`{ pollId | null }`).
- `DockPreview` (`{ pollId | null, cursor | null }`): phase 2, defined but **never sent**.

**View `Channel<PollViewEvent>`** (one per attached view, its poll only):
- `ConnectionStateChanged`, `PollStateChanged`: never dropped or coalesced; a pending `PollUpdate` is flushed first.
- `PollUpdate` (`pollId, seq, at, slaveId, function, startAddress, values, roundTripMs`): at most one per 50 ms per view, latest wins; `seq` strictly increases per poll; a pending update of an old definition is discarded on Apply.
- `PollConfigChanged` (`PollConfig`, flattened), `PollCounters` (`PollCounters`, at most one per 100 ms per view), `PollRemoved` (`{ pollId }`, last event), `ProfileNameChanged` (`{ name }`), `PrefsChanged`, `ViewDetached` (`{ pollId, reason: "poppedOut" | "docked" | "replaced" | "closed" }`, last event), `HandoffRequested` (`{ pollId }`, native views only).

### Scheduling (DES-002 section 7, `crates/modbus-master/src/scheduler.rs`)
One request in flight; queued writes first (one FIFO); then the running poll with the earliest `nextDue` that is not in the future, ties to the least recently served, then the lower poll id; `nextDue = start + scanRate` (one immediate request after a slow cycle, never a burst); an overdue poll keeps its old deadline, so it waits for at most the other 15 polls. List order and host never matter. `PollCounters.effectiveScanMs` = mean interval of the last (up to) 10 cycle starts since the poll (re)started, null with fewer than 2; the UI applies the 1.5 x rule. `linkLoadPct` = share of the last 2 s the link was busy with a request (0 without a link).

### Counters
BE-001 semantics per bucket: `requests` written, `responses` valid replies including exceptions, `errors` exceptions plus bad responses, `timeouts`. A poll request counts in `total` and in that poll; a write in `total` and `writes`, never in a poll. A deleted poll's counts stay in `total`. Discarded bytes count nowhere. `PollCounters.lastOkAt` is the time of the last valid reply of the current definition (null after Apply, Disconnect and Dismiss).

### Dev/test tool additions (`crates/dev-sim-slave`)
- `fault <kind> ... [times=N] [unit=<id>]`: only requests to that unit id are faulted; other units are answered normally and do not use up `times=N`. `status` shows `@unit<id>`.
- The log prints `conn=<n> OVERLAP # the next request arrived <t> ms after this request, before this reply` when a master sends a request before the previous reply was sent, so "no overlap" can be asserted from the log.
- Rule with an injected delay (REV-004 m7): during a `fault delay` the line is checked every 2 ms. A request that arrives at least the master's timeout after the delayed request is logged as `conn=<n> ABANDONED # the next request arrived <t> ms into an injected delay of <d> ms: the master timed out and moved on (not an overlap)`: correct master behaviour. Earlier than that, or without a delay, it is `OVERLAP`. The master's timeout is told with the new control command `master-timeout <ms>` (1-600000, default 50 = the smallest timeout Modbus Master accepts); set it to the connection's timeout for an exact verdict.
- All three still need a line in `docs/SETUP.md` section 4 (not edited by the backend; Q-BE2-06). SETUP.md currently says "Expect none" for `OVERLAP`; with `fault delay` longer than the master timeout, `ABANDONED` lines are expected.
