## Bulk coordinator (poll_bulk.rs + session/bulk.rs) - correctness summary

Verified good: prepare checks for distinct, existing ids and capacity (16) before anything changes (`bulk.rs:316-362`). Execute revalidates the frozen guards and the order revision, takes view readiness leases, waits at most 1 s, then commits every definition in one actor turn. List publication is held back during the reservation (`session.rs` `emit_list`), so exactly one `PollListChanged` goes out at release. Post-commit OS failures become `issues`; they never roll back definitions (`poll_bulk.rs:112-164`). A dropped lease records the result with "interrupted" issues (`bulk.rs:49-61`, `514-532`). Same-token replays return the recorded result (`bulk.rs:94-99`). The scheduler handling of copies matches the single-duplicate path, because `entry()` clears `request` unless the copy is connected and active (`session.rs:2021, 2036`). Native-window destruction is tied to an incarnation generation (`tauri_desktop.rs:148-175`, `session.rs native_incarnation_destroyed`), which closes the earlier REV-010 M-1 race. The tests are meaningful: they cover ordering/atomicity, capacity, ABA, readiness timeout, ack identity, cancelled futures, same-token concurrency, post-commit create/place/show/destroy failure, and a delayed old destroy.

### Major

**M-1 (major, process) The whole feature set landed in one commit with a misleading message, and every artifact, including the "independent" reviews, came from the same tool.**
- Where: commit `f6af3d1` message ("Add new end-to-end tests for value color rules and sidebar functionality"); `docs/reviews/REV-013-values-sidebar.md`, `REV-010-bulk.md`, `REV-011-bulk-fault-hook.md`, `REV-012-gridstack-workspace.md`.
- Problem: five features (REQ-004..008), a profile schema bump from 2 to 5, five new Tauri commands, a new runtime dependency (`gridstack` 14.0.0, `apps/desktop/package.json`), and changed error codes (`profiles_save`: `validation` -> `invalidProfile`, `profiles.rs:87`) ship under a commit message that only mentions e2e tests. The REQ/DES/BE documents, the QA reports and the reviews were all produced in the same session, so the CLAUDE.md "independent reviewer" gate was not actually met. REV-012 contains no file:line findings at all.
- Decision drift: `docs/questions.md` D-005-02 still says "max 16 rules" and "schema 3", and D-006-02 says "schema3", while the code ships 256 rules (`color_rules.rs:87`) and schema 5 (`profile.rs:15`). `BE-005`/`BE-006` still describe schema 3. The owner corrections are recorded only in REQ-005 and STATUS, not as decision rows.
- Failure scenario: anyone bisecting or reading `git log` for the schema 5 change or the 256-rule limit finds an "e2e tests" commit and contradictory decision rows. A later agent that follows D-005-02 might "fix" the limit back to 16.
- Suggested fix: add D-005-03 (256 rules, custom colors, advisory contrast) and D-00x (schema 5) to `docs/questions.md`, and update BE-005/BE-006. This file is the independent review. In future, split commits per feature with accurate messages.

**M-2 (major, release docs) The CHANGELOG "Known limitations" now overstates verification. The CHK-004..008 checklists are not signed off.**
- Where: `CHANGELOG.md:78-81` (in f6af3d1), compared with `docs/qa/REPORT-018-checklist-status.md` (3 PASS / 58 PARTIAL / 10 OPEN of 71 ids; for example CHK4-A6 and CHK4-A7 are OPEN) and STATUS "OPEN: full CHK-004..007 sign-off".
- Problem: the earlier honest limitation ("not run in a real window yet") was replaced by "the available simulator and single-monitor real-window cases have been verified". REPORT-018 says many simulator and real-window clauses are still PARTIAL or OPEN. The CLAUDE.md DoD requires every checklist item to be marked pass/fail.
- Failure scenario: a 0.2.0 tag carries release notes that claim coverage the QA record contradicts. Users of a pre-release then rely on keyboard/accessibility and bulk-window behavior that was never verified end to end.
- Suggested fix: before tagging, reword the limitation, for example: "Checklists CHK-004..008 are partially verified (REPORT-018: 3 pass, 58 partial, 10 open); keyboard/screen-reader, mixed-DPI, RTU hardware and soak checks remain." Also add: "Performance with more than 16 color rules per poll is not measured" (see m-6).

### Minor

**m-1 `crates/modbus-master/src/session.rs:221` (`call`): every actor call deep-clones the full config of every poll twice, even when no bulk plan exists.**
- Problem: `bulk_guards()` clones `PollConfig` (aliases up to 2000, scale overrides, up to 256 color rules) for all polls before and after each `call`, and `observe_bulk_change` compares the clones. This runs on the actor task that also drives the poll scheduler.
- Failure scenario: with 16 polls x 2000 aliases, each `set_workspace_layout`, `set_native_placement`, `detach_view`, write, or each 10 ms readiness check (`bulk.rs:118`) clones about 64k strings on the actor. That can add scan-rate jitter at 20 ms scan rates while the user drags a window.
- Suggested fix: revisions only matter while `bulk.plan` or `bulk.reservation` is `Some`. Skip both snapshots when neither exists, and on `prepare_bulk` bump every target's revision baseline instead. Alternatively, bump a per-poll revision counter inside the mutators.

**m-2 `crates/modbus-master/src/session/bulk.rs:498-505`: bulk duplicate does not emit counters, unlike the single path.**
- Problem: `after_add` (`session.rs:2052-2061`) calls `emit_counters(None)` after inserting a poll. The bulk commit inserts copies into the scheduler and list but never calls `emit_counters`. `remove_poll` (used by bulk delete) does.
- Failure scenario: while disconnected or paused (no request ticks), the W1 `ConnectionCounters.polls` sent to the frontend has no entries for the new copies until some later counters emission. I did not check how the UI renders a missing entry.
- Suggested fix: call `self.emit_counters(None)` once after the splice, or in `release_bulk` when a duplicate committed.

**m-3 `apps/desktop/src-tauri/src/commands/value_inputs.rs:174`: wrong user-visible schema number, plus stale "schema 3" docs.**
- Problem: the error says "Expected profile schema 3." but `PROFILE_SCHEMA_VERSION` is 5. The doc comments are stale too: `crates/shared-types/src/profile.rs:1, 35, 40` ("schema 3", "3. Checked by the backend"), the generated `Profile.ts` ("A saved Modbus Master setup, schema 3."), and `crates/platform/src/mm_profile.rs:121`.
- Suggested fix: use `format!("Expected profile schema {PROFILE_SCHEMA_VERSION}.")` and update the comments, then regenerate bindings.

**m-4 `value_inputs.rs:147-149` (`decode`): raw serde text leaks into user errors with a misleading field.**
- Problem: any decode failure after the shape checks becomes `AppError { field: "view", message: <serde error> }`, including for profiles (`InvalidProfile`) and `mm_add_poll`. The serde text looks like "unknown field `x`, expected one of ..." and is not UI-grade English.
- Suggested fix: map to a fixed message ("This profile is damaged." / "Enter a supported poll setup.") and log the serde detail with `tracing`.

**m-5 `RuleSection.tsx:477-482` and `RuleMarker.tsx`: custom colors bypass the orange-means-warning rule and drop warning semantics.**
- Problem: choosing "Custom colors" always sets `highlight: "lime"`. A custom rule can therefore use orange (for example `#fa8130`) without being a warning rule, which contradicts REQ-005 ("an orange choice must explicitly denote a warning rule") and the CLAUDE.md visual rule. Switching an existing Warning rule to Custom also silently removes the "⚠" marker and the "Warning rule." accessible text (`color-rules.ts` descriptions).
- Failure scenario: an operator configures an orange custom color for a normal state. Other users read it as a warning, and screen-reader users get no warning announcement for a rule the author meant as a warning.
- Suggested fix: keep "warning" as a separate flag independent of the color source, so a custom-colored rule can still be a warning. Show an advisory when a custom background is near the warning token and the rule is not a warning. If the owner has accepted arbitrary colors, record that as a decision in `docs/questions.md`.

**m-6 Perf evidence covers 16 rules, but the shipped limit is 256.**
- Where: `e2e/tests-integration/25-report017.spec.ts:183` (`"16 rules unsigned16"`), `docs/qa/CHK-005-value-color-rules.md:41` (D2 still says 16 rules), and `lib/color-rules.ts` `matchRule`, which reparses each threshold string with regex/`BigInt` per cell, per rule, per render.
- Problem: the owner-motivated case (125 registers, each with its own static rule, plus conditional rules) is not measured against the REQ-005 AC6 limit (125 registers at 100 ms, no long tasks). Per-register rules exit on the range check before parsing, so the risk is moderate. Whole-poll conditional rules near the limit (up to 256 x 125 parses per update) are unmeasured.
- Suggested fix: precompile thresholds once per applied rule set (memoize by the `colorRules` array identity), and rerun the REPORT-017 capture with 125 static plus about 16 conditional rules.

**m-7 `apps/desktop/src/tools/modbus-master/components/sidebar/PollBulkActions.tsx:20`: recovery rows for deleted polls show the runtime id as a fake name.**
- Problem: `RetryWindowCleanup` issues refer to polls that are already removed, so `s.polls[id]` is undefined and the label becomes `Poll ${issue.pollId}`, a runtime id rather than a name.
- Failure scenario: the user deletes "Boiler" (runtime id 7) while a poll actually named "Poll 7" still exists. The notice reads "Poll 7: The poll window could not be closed. Retry window cleanup.", which points at the wrong poll.
- Suggested fix: carry the poll name in `PollBulkWindowIssue` (ts-rs DTO), or keep a name map from `plan.targets` in the store.

**m-8 `crates/modbus-master/src/session/bulk.rs:115-123`: the readiness timeout reports a misleading cause.**
- Problem: any view that has not acked within 1 s (a slow or busy WebView2, a native window still loading) returns "Close dialogs in the selected poll windows and try again." even when no dialog is open. There is no distinct timeout message.
- Suggested fix: return a separate message for the timeout ("A poll window did not respond. Try again.") and keep the dialog message for an explicit `ready: false` ack.

**m-9 `apps/desktop/src/app/tokens.test.ts:61-63`: the hard-coded-color guard exempts two entire files.**
- Problem: `RuleSection.tsx` and `rule-draft.ts` are excluded from the hex-literal check. They repeat the token values `#EDEFF2` / `#312F2E` at `RuleSection.tsx:481, 507, 511-512` and `rule-draft.ts:117-118`. Any future hard-coded color in those files would pass the guard unnoticed.
- Suggested fix: export one `DEFAULT_RULE_COLORS` constant from a tokens module (for example `shared/lib/tokens.ts`, kept in sync with `styles.css` by a test), and exempt only that file.

**m-10 `e2e/tests-integration/10-profiles.spec.ts:56, 63`: the CHK2-N5 case now passes for a different reason.**
- Problem: the title and the `Bad-v3` fixture assert that "schema 3" is unreadable. Schema 3 is now a supported, migrated version (`mm_profile.rs` `3..=5`). The fixture `{schemaVersion:3, name, polls:[]}` is still rejected only because required fields are missing.
- Suggested fix: use `schemaVersion: 6` for the "newer" case, and add a valid schema 3 fixture that must open with the migration notice.

### Nits

- `crates/modbus-master/src/session.rs:2227`: `rules[index]` uses an index parsed from an error string with `unwrap_or(0)`. It cannot panic only because of an invariant. Use `rules.get(index).map_or("", |r| r.name.as_str())`.
- `session/bulk.rs:109-113`: the `Pending` branch polls every 10 ms with no deadline. If the original execute ever hangs inside an OS window call, the same-token retry hangs too. Add an upper bound.
- `poll-bulk.store.ts:129`: the announcement reads "Deleted 1 polls." / "Duplicated 1 polls." Pluralize.
- `crates/shared-types/src/layout.rs` (`GridRect`): the doc comment is copy-pasted from `WorkspaceRect` ("A workspace sub-window rectangle"). It should describe GridStack cells.
- Threshold length is checked before trimming in Rust (`color_rules.rs:111`) and after trimming in TypeScript (`color-rules.ts` `parseThreshold`). A padded 250-digit threshold passes the editor and is rejected by the backend.
- `CHANGELOG.md` `[Unreleased]` has two `### Changed` headings (lines 14 and 66). Its `### Fixed` entries describe fixes to features that were never released. Merge them into Added/Changed.

## Test quality

The Rust bulk tests (`crates/modbus-master/tests/bulk.rs`, 14 cases; `poll_bulk.rs` 3 cases) and the color-rule validation tests (`color_rules.rs`, `value_inputs.rs`) assert concrete outcomes, including boundaries: 256/257 rules, ±18446744073709551615, 64/65-character names, and the 15+2 capacity case. `poll-bulk.store.test.ts` covers stale replies across profile reset and lost responses. The e2e specs contain real assertions (16 to 83 `expect` calls per file, no `.only`, `skip` or `fixme`). The weak points are m-6 (perf at 16 rules only) and m-10 (a test passing for the wrong reason). Integration specs are named after report numbers (`22-report011.spec.ts` and so on) instead of checklist ids, which makes traceability from CHK ids harder.

## Verdict

**Approve (no blocker).** I found no correctness, concurrency, security or hard-rule violation that blocks release. The bulk transaction design is sound and well tested.

**Release recommendation:** OK to release as a **0.2.0 pre-release** (not a stable 0.2.0) once **M-2 is fixed**. M-2 is a CHANGELOG wording change that states the open checklist items honestly. It should be done before tagging, using `pnpm version:set 0.2.0` per CLAUDE.md. M-1 (decision rows) and m-3 (wrong schema number in a user-visible message) are cheap and should go in the same change. The other minor findings can follow in a 0.2.x update. A stable 0.2.0 should wait for CHK-004..008 sign-off (REPORT-018 OPEN/PARTIAL items) and the m-6 performance measurement.
